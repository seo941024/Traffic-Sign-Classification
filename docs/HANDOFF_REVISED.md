# A. 실측 후 수정이 필요한 부분

## A-1. 클래스 체계 (원본 13절 대체)

### 원본
> 예시: `stop`, `speed_30`, `speed_50`, `speed_60`, `no_entry`, `no_parking`, `left`, `right`, `straight`

### 실제
**이런 의미 라벨은 AI-Hub 데이터에 존재하지 않는다.**

AI-Hub는 표지판의 **의미**가 아니라 **생김새**만 라벨링한다.

```
shape : circle / triangle / rectangle
color : red / blue / yellow
type  : restriction / instruction / caution / pedestrian   ← 결측 많음
text  : 대부분 "0" → 속도 숫자로 쓸 수 없음
```

### 개정: shape × color 6개 클래스

| 클래스 | 표지판 유형 | ≥24px 장수 |
|---|---|---|
| `circle_red` | 규제표지 (속도제한·진입금지) | 8,153 |
| `triangle_yellow` | 주의표지 | 3,564 |
| `circle_blue` | 지시표지 | 2,378 |
| `triangle_red` | 규제표지(삼각) | 1,254 |
| `triangle_blue` | 지시표지(삼각) | 1,237 |
| `rectangle_blue` | 안내표지 | 872 |

### 이 변경이 프로젝트를 훼손하지 않는 이유

원본 22·36절이 요구한 질문들 — *"Flatten을 하면 어떤 문제가 생기는가"*,
*"Convolution은 무엇을 계산하는가"* — 은 **클래스가 무엇이냐와 무관하다.**

오히려 shape×color는 **CNN의 우위를 더 선명하게 보여준다.**

- `circle` vs `triangle` vs `rectangle` = **형태(윤곽선) 구분**
- Convolution의 얕은 층이 학습하는 것이 바로 **선·모서리·방향**이다
- Flatten된 ANN/DNN은 "어느 픽셀이 서로 인접한지"를 모르므로 윤곽선 판단이 근본적으로 불리하다

즉 **"CNN이 왜 이미지에 적합한가"를 증명하기에 원본 클래스 안보다 오히려 더 적합하다.**

### 원본 22절 혼동 쌍 예시도 교체

| 원본 | 개정 | 무엇을 보는가 |
|---|---|---|
| `speed_30` ↔ `speed_50` | `circle_red` ↔ `circle_blue` | **색상**만 다르고 형태 동일 |
| `left` ↔ `right` | `triangle_blue` ↔ `triangle_red` | **색상**만 다르고 형태 동일 |
| — | `circle_*` ↔ `triangle_*` | **형태**가 다름 |

**핵심 가설**: ANN/DNN은 색상 구분은 그럭저럭 하지만(픽셀 평균색으로 가능)
**형태 구분에서 무너질 것이다.** Confusion Matrix로 이걸 확인하면
"공간 정보를 못 쓴다"는 주장에 직접적인 증거가 붙는다.

## A-2. 입력 크기 (원본 29.3절 수정)

### 원본
> `64 × 64 × 3` = 12,288 input features

### 실제 bbox 짧은 변 분포

| p25 | **p50** | p75 | p90 | p95 |
|---|---|---|---|---|
| 12px | **17px** | 26px | 39px | 48px |

**절반이 17px 이하다.** 주행 영상이라 표지판이 대부분 멀리 있다.

### 개정: 32×32×3 = **3,072** features

17px짜리를 64×64로 키우는 건 **없는 정보를 늘려서 만드는 것**이다.
(GTSRB 등 공개 표지판 데이터셋도 32×32가 표준이다.)

**원본의 논지는 그대로 유효하다:**

```
32 × 32 × 3 = 3,072 input features
→ Dense(3072 → 1024) 하나가 3,146,752 파라미터
→ Conv2d(3 → 32, 3×3) 은 896 파라미터
```

3,500배 차이다. 12,288이든 3,072이든 **"Dense는 입력 크기에 비례해 늘고
Conv는 안 는다"**는 결론은 동일하다.

# B. 원본에 없어서 보완이 필요한 부분

## B-1. ⭐ Baseline 없이는 정확도를 해석할 수 없다

원본 21절은 여러 지표를 기록하라고 하지만 **비교 기준선(baseline)을 제시하지 않는다.**

정확도 65%가 좋은 건지 나쁜 건지는 **baseline 없이는 판단 불가능**하다.

반드시 같이 기록해라:

| Baseline | 계산 | 의미 |
|---|---|---|
| **무작위** | `1 / 클래스수` = 16.7% | 이보다 낮으면 학습이 안 된 것 |
| **최빈 클래스** | 가장 많은 클래스 비율 | **이걸 못 넘으면 모델이 무의미하다** |

클래스당 800장으로 균형을 맞추면 둘 다 약 16.7%가 된다.

> 면접에서 *"CNN이 92% 나왔습니다"*보다
> *"무작위가 16.7%인데 ANN이 71%, CNN이 92%였습니다"*가 훨씬 강한 진술이다.

## B-2. ⭐ 클래스 불균형 → Accuracy만 보면 속는다

원본은 클래스 불균형을 9절에서 한 번 언급하고 넘어간다.
실제로 `circle_red`(8,153) vs `rectangle_blue`(872)로 **9.4배 차이**다.

**대응 두 가지 (둘 다 적용했다):**

1. 클래스당 상한 800장으로 **균형 샘플링** (`MAX_IMAGES_PER_CLASS`)
2. **Macro F1**을 Accuracy와 함께 기록
   → Macro F1은 클래스 크기를 무시하고 평균내므로 소수 클래스 성능이 그대로 드러난다
   → Accuracy는 높은데 Macro F1이 낮으면 **다수 클래스만 맞히고 있다는 신호**다

## B-3. ⭐ 고정 Epoch은 모델 간 비교를 왜곡한다

원본 19절은 "Epoch을 동일하게"라고 하지만, 이건 **오히려 불공정할 수 있다.**

- DNN은 파라미터가 많아 **빨리 과적합**한다
- CNN은 더 오래 개선된다

30 epoch 고정으로 돌리면 **DNN은 과적합된 상태로, CNN은 덜 학습된 상태로** 비교하게 된다.
그건 구조의 차이가 아니라 **멈추는 시점의 차이**다.

**개정**: Early Stopping을 세 모델에 **동일한 patience**로 적용한다.

```python
EARLY_STOPPING_PATIENCE = 7   # val loss 기준, 세 모델 동일
```

각자 자기 최적 지점에서 멈추게 하는 것이 공정하다.
**patience 값 자체가 동일하다는 것이 "동일 조건"의 진짜 의미다.**

부수 효과: 학습 시간 비교가 의미를 갖는다. "몇 epoch 만에 수렴했는가"도 기록 항목이 된다.

## B-4. ⭐ 재현성 — Seed 고정 위치

원본에 재현성 언급이 없다. 없으면 **돌릴 때마다 결과가 달라져서** 비교가 무의미해진다.

**중요**: 모델을 만들기 **직전마다** seed를 다시 고정해야 한다.

```python
for name in ("ann", "dnn", "cnn"):
    set_seed(config.SEED)        # ← 여기. 루프 밖이 아니다
    model = build_model(name)
```

루프 밖에서 한 번만 고정하면 ANN 학습이 난수 상태를 소모해서
DNN과 CNN이 서로 다른 초기화를 받는다. 그러면 조건이 어긋난다.

## B-5. ⭐ Softmax를 넣지 않은 것에 대한 주의

원본 20절은 "CrossEntropyLoss를 쓴다"고만 한다. 실무에서 가장 흔한 사고 지점이다.

이 프로젝트의 모델들은 마지막 층에 **softmax를 넣지 않고 logits을 그대로 출력한다.**

| 프레임워크 | 반드시 이렇게 |
|---|---|
| PyTorch | `nn.CrossEntropyLoss()` — 내부에서 log_softmax 수행 |
| Keras | `SparseCategoricalCrossentropy(**from_logits=True**)` |

**`from_logits=True`를 빠뜨리면 loss가 조용히 잘못 계산된다. 에러는 안 난다.**
학습이 되긴 하는데 성능이 이상하게 낮게 나오고, 원인 찾기가 어렵다.

반대로 softmax를 넣고 `from_logits=True`를 쓰면 **softmax가 두 번** 적용된다.

## B-6. ⭐ 데이터 누수 — 원본이 놓친 경로

원본 15절은 "연속 촬영 프레임"을 지적한다. **맞지만 더 직접적인 누수가 있다.**

**사진 한 장에서 표지판을 여러 개 자른다.** (샘플 파일 하나에 6개가 있었다.)

같은 사진에서 나온 crop들은 **배경·조명·날씨·카메라·시각이 완전히 동일**하다.
이게 train과 test에 나뉘면 모델은 표지판이 아니라 **그날의 촬영 조건**을 외워서 맞힐 수 있다.

**대응**: crop 파일명을 `{원본stem}__{순번}.jpg`로 지어 원본을 복원 가능하게 했고,
분할 시 원본 단위로 통째로 묶는다. 여기에 원본 15절의 시퀀스 단위 묶기를 추가로 적용한다.

## B-7. 파라미터 수를 맞춘 대조 실험 (선택, 하지만 강력함)

원본 19절은 *"완전히 동일한 파라미터 수를 맞추는 것이 항상 필요한 것은 아니다"*라고 한다.
맞다. 하지만 그러면 이런 반론이 가능하다:

> *"CNN이 이긴 건 구조 때문인가, 아니면 우연히 파라미터 배분이 좋아서인가?"*

**대조 실험**: DNN의 hidden units를 줄여 CNN과 파라미터 수를 비슷하게 맞추고 다시 돌린다.

```python
# CNN ≈ 620K 파라미터에 맞춘 DNN
DNN_HIDDEN_UNITS = (192, 128, 64)   # → 약 620K
```

**파라미터가 같은데도 CNN이 이긴다면**, 그건 구조 때문이라는 결정적 증거다.
면접에서 이 실험을 했다고 말할 수 있으면 수준이 달라진다.

## B-8. 학습 곡선으로 과적합을 읽는 법 (원본에 없음)

원본 21절은 Train/Val Loss를 기록하라고만 하고 **어떻게 해석하는지** 말하지 않는다.

| 패턴 | 진단 | 대응 |
|---|---|---|
| train↓ val↓ 둘 다 | 정상 학습 중 | 계속 |
| train↓ **val↑** | **과적합** | Early stopping이 잡아준다 |
| 둘 다 높은 채 정체 | 과소적합 / lr 문제 | 구조나 lr 재검토 |
| val이 심하게 출렁 | batch가 작거나 val이 작음 | 데이터 확인 |

**예상**: DNN에서 train↓ val↑ 패턴이 가장 먼저 나타날 것이다.
파라미터가 가장 많아 외우기 쉽기 때문이다. **이게 관찰되면 그 자체가 좋은 분석 재료다.**

## B-9. 예상과 다른 결과가 나왔을 때 (원본 24절 보강)

원본은 *"예상과 다른 결과가 나온다면 그 원인을 분석한다"*고만 한다. 구체적 체크리스트:

**CNN이 예상보다 나쁘다면 — 이 순서로 확인해라**

1. **데이터부터 의심해라.** crop이 제대로 됐나? (`03_verify_crops.py`)
   모델을 의심하기 전에 데이터를 본다. 대부분 여기서 나온다.
2. 입력 정규화가 두 프레임워크에서 같은가?
3. `from_logits` 설정이 맞나?
4. 학습이 수렴했나? (Early stopping이 너무 일찍 잘랐을 수 있다)
5. lr이 CNN에 너무 큰가? (구조상 민감도가 다르다)

**ANN/DNN이 예상보다 좋다면**

- 32×32는 작은 이미지라 Flatten의 불리함이 덜 드러날 수 있다
- shape×color는 **색상만으로도 상당 부분 구분 가능**하다
  (`circle_red` vs `circle_blue`는 평균 색만으로 갈린다)
- → **Confusion Matrix에서 "형태가 다른 쌍"만 따로 보면** CNN의 우위가 드러날 것이다
  (`circle_*` ↔ `triangle_*` 혼동률을 모델별로 비교)

이건 실패가 아니라 **더 정밀한 분석의 출발점**이다.

## B-10. 확장 아이디어 — traffic_light를 버리지 마라

원본에 없는 항목이다. 데이터에 `traffic_light`가 **39,888개** 있고 이런 속성을 갖는다.

```json
"attribute":[{"red":"off","green":"on","yellow":"off",
              "left_arrow":"off","x_light":"off","others_arrow":"off"}]
```

→ 신호등 상태 분류(`red`/`green`/`yellow`/`left_arrow`)로 **클래스를 4개 더** 만들 수 있다.

→ 데이터셋 이름 자체가 "**신호등**-도로표지판 인지 영상"이므로 데이터 취지에도 맞다.

**1차 실험은 표지판 6종으로 하고, 확장 1로 신호등을 추가하는 것을 권한다.**

## B-11. Data Augmentation 주의 (원본 34절 보강)

원본은 *"좌회전/우회전에 Horizontal Flip은 안 된다"*고 정확히 지적했다.
개정된 클래스 체계에서는 주의 지점이 달라진다.

| 기법 | 가능? | 이유 |
|---|---|---|
| Horizontal Flip | ⚠️ 조건부 | shape×color에서는 의미가 안 바뀐다. 단 **신호등 좌회전 화살표는 뒤집히면 안 된다** |
| **색상 변경 (Hue/Saturation)** | ❌ **절대 금지** | **색이 클래스 그 자체다.** red→blue가 되면 라벨이 틀려진다 |
| Rotation | ⚠️ 소각도만 | 삼각형을 크게 돌리면 형태 인식이 무의미해진다. ±10° 이내 |
| Brightness / Contrast | ✅ | 조명 변화는 실제로 존재한다 |
| Random Crop | ⚠️ | 테두리가 잘리면 형태 정보가 사라진다. 여유를 적게 |
| Noise | ✅ | |

**1차 실험에서는 augmentation을 쓰지 않는다.**
세 모델의 조건을 동일하게 유지하는 것이 우선이고, augmentation은
모델마다 다르게 작용할 수 있어 구조 비교를 흐린다.
